# Формат данных Mind Map — спецификация для нейросетевого агента

Этот документ описывает JSON-формат данных приложения **jLearn mindmap** (файл `mindmap/`) для агента,
который наполняет и модифицирует диаграмму по запросу пользователя (создание узлов, добавление
заметок, создание тестов и т.д.). Формат — единственный источник истины для сохранения/загрузки
(`localStorage`) и для экспорта/импорта в файл (кнопки «Экспорт JSON» / «Импорт JSON» в приложении).

Текущая версия формата: **5**.

---

## 1. Общая структура файла

```jsonc
{
  "version": 5,
  "rootId": "n1a2b3c4",
  "nodes": {
    "n1a2b3c4": { /* узел */ },
    "n1a2b3c5": { /* узел */ }
  }
}
```

- `version` — целое число, номер версии формата (см. раздел 7). Всегда пишите текущую версию (5).
- `rootId` — id корневого узла. Должен присутствовать в `nodes`.
- `nodes` — плоский словарь `{ id: node }`. Дерево строится через поле `parentId` у каждого узла
  (НЕ через вложенность в JSON — все узлы, включая глубоко вложенные, лежат на одном уровне словаря
  `nodes`).

### Правила дерева (обязательны для валидного результата)

- Ровно **один** корневой узел: узел с `id === rootId` и `parentId: null`. У всех остальных узлов
  `parentId` должен указывать на существующий id в `nodes`.
- Циклы запрещены (узел не может быть предком самого себя через цепочку `parentId`).
- Корень **нельзя** удалять программно средствами приложения, но как агент, генерирующий файл
  целиком, вы просто обязаны всегда включать ровно один корень.
- Идентификаторы (`id`) — произвольные уникальные строки. Родное приложение генерирует их в виде
  `"n" + base36(timestamp) + base36(counter)` (например `"nmsqk11f81"`), но для генерации агентом
  подходит любая схема, гарантирующая уникальность в пределах файла (например `"n1"`, `"n2"`, ...
  или UUID). Единственное жёсткое требование — синтаксис: непустая строка.

## 2. Объект узла (`node`)

```jsonc
{
  "id": "n1a2b3c5",
  "type": "main",
  "text": "Текст узла",
  "parentId": "n1a2b3c4",
  "data": {
    "direction": "right",
    "comment": "Короткая подпись под узлом",
    "note": "# Заметка в Markdown\n\nТекст...",
    "offset": { "dx": 12, "dy": -8 },
    "test": { /* см. раздел 4 */ },
    "testResult": { /* см. раздел 5 */ },
    "marked": true
  }
}
```

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `id` | string | да | Уникальный идентификатор узла, совпадает с ключом в `nodes`. |
| `type` | string | да | Один из зарегистрированных типов узла: `"main"`, `"test"`, `"link"` (см. раздел 3). |
| `text` | string | да | Заголовок узла, отображается в самой mind-map (НЕ Markdown, обычный текст). |
| `parentId` | string \| null | да | `null` только у корня; иначе id родительского узла. |
| `data` | object | да (может быть `{}`) | Контейнер необязательных атрибутов — см. ниже. Все ключи внутри `data` необязательны; отсутствие ключа означает «атрибут не задан», а не пустое значение. |

### 2.1 `data.direction` — направление ветви (`"up" | "down" | "left" | "right"`)

Диаграмма — радиальная: корень в центре, а 4 направления определяют, в какую сторону экрана растёт
ветвь. **Хранится ТОЛЬКО у прямых детей корня** (узлов, чей `parentId === rootId`). У более глубоких
потомков это поле не устанавливается — они автоматически наследуют направление ветви, к которой
принадлежат (вычисляется приложением по дереву).

- Обязательно для прямых детей корня. Если не хотите продумывать конкретное направление —
  используйте `"right"` (значение по умолчанию в приложении).
- НЕ добавляйте `direction` узлам, у которых `parentId !== rootId` — это лишнее и будет
  проигнорировано приложением при следующей же ручной операции (сброс/пересчёт направления).

### 2.2 `data.comment` — краткий комментарий-подпись (строка)

Необязательный короткий (может быть многострочным) текст, который отображается **под** узлом
на диаграмме мелким шрифтом. Это НЕ Markdown и НЕ отдельный тип узла — обычный текст-аннотация.
Не путайте с `data.note` (полноценная заметка, см. 2.3).

- Отсутствие поля = «комментария нет».
- Пустая строка трактуется приложением как «удалить комментарий» — не создавайте `"comment": ""`,
  просто не добавляйте ключ.

### 2.3 `data.note` — заметка узла (Markdown, строка)

Полноценная заметка узла, отображаемая и редактируемая в боковой панели «Заметки». Формат текста —
**Markdown**, подмножество (см. раздел 6 «Поддерживаемый Markdown»).

- Отсутствие поля = «заметки нет».
- Пустая/пробельная строка трактуется приложением как «заметки нет» — не создавайте `"note": ""`,
  просто не добавляйте ключ.
- Разрешено использовать `\n` для переносов строк внутри JSON-строки.

### 2.4 `data.offset` — ручное смещение узла на холсте

```jsonc
"offset": { "dx": 12.5, "dy": -8.0 }
```

Пиксельное смещение узла (и всей его ветви) относительно позиции, которую вычислил бы
автоматический радиальный layout. Это чисто визуальная подстройка пользователем через drag&drop
внутри приложения.

- **Обычно агенту НЕ следует устанавливать это поле** — оставляйте узел на автоматической позиции
  (просто не добавляйте `offset`). Поле имеет смысл только как результат ручного перетаскивания
  пользователем в самом приложении.
- Если импортируете/модифицируете уже существующий файл, где `offset` присутствует у узла — можно
  сохранить его как есть, если вы не меняете структуру дерева. Но если вы меняете `parentId` этого
  узла (переносите его в другое место дерева), **удалите** поле `offset` — старое смещение теряет
  смысл при смене родителя (сама программа делает то же самое при перетаскивании узла мышью).

### 2.5 `data.test` и `data.testResult`

Поля тестирования — см. разделы 4 и 5 ниже. Обычно устанавливаются только у узлов с
`"type": "test"`, но формально это независимые атрибуты, доступные любому узлу (как и `comment`/`note`).

### 2.6 `data.marked` — отметка узла (boolean)

Чисто визуальный маркер: у отмеченного узла рамка окрашивается в зелёный цвет вне зависимости от
его типа. Не влияет на структуру дерева и логику приложения — переключается кнопкой «Выполнен» в
группе «Узлы» тулбара.

- Отсутствие поля или `false` = «не отмечен» — это подавляющее большинство узлов.
- Пишите `"marked": true` только когда узел действительно должен быть отмечен; не добавляйте
  `"marked": false` — используйте отсутствие поля.
- Корневой узел не отмечается приложением (кнопка игнорирует клик, если выделен root) — не
  устанавливайте это поле у корня.

## 3. Типы узлов (`type`)

Реестр типов **фиксирован кодом приложения** (`mindmap/js/nodeTypes.js`) — агент не может вводить
новые типы через данные, только использовать существующие:

| `type` | Название в UI | Назначение | Может иметь детей |
|---|---|---|---|
| `"main"` | Узел | Обычный смысловой узел карты (по умолчанию) | да |
| `"test"` | Тест | Узел, к которому обычно привязывается `data.test` (см. раздел 4) | да |
| `"link"` | Ссылка | Узел-ссылка (смысловая пометка «это ссылка на внешний ресурс») | да |

Примечания:
- Все три типа технически могут иметь детей и могут получить `comment`/`note`/`test` — типы не
  накладывают структурных ограничений сами по себе, это лишь смысловая категория + визуальное
  оформление (значок перед текстом/цвет текста). Рамка узла по умолчанию одного цвета у всех типов;
  зелёной она становится только при `data.marked: true` (раздел 2.6), вне зависимости от типа.
- Если пользователь просит «добавить узел» без уточнения — используйте `"main"`.
- Если пользователь просит «добавить тест» или у узла явно должен быть тест — используйте `"test"`
  и заполните `data.test` (раздел 4). Технически `data.test` можно повесить и на узел `"main"`, но
  по соглашению используется тип `"test"`, чтобы в интерфейсе автоматически появлялась кнопка
  прохождения теста при клике на узел (боковая панель распознаёт тест-вью по типу узла).
- Если пользователь явно просит новый тип узла — это НЕ делается через данные; сообщите, что
  требуется изменение кода приложения (реестр типов зашит в `nodeTypes.js`), либо используйте
  ближайший подходящий существующий тип + `comment`/`note` для уточнения.

## 4. `data.test` — определение теста

Создаётся только внешним инструментом (в том числе вами, агентом) — в самом приложении UI для
редактирования вопросов отсутствует. После того как вы записали `data.test` в узел (обычно типа
`"test"`), пользователь проходит тест через боковую панель в приложении.

```jsonc
"test": {
  "title": "Тест по интерфейсу",
  "description": "Проверка знаний по работе с mind map.",
  "passThreshold": 70,
  "estimatedMinutes": 10,
  "questions": [
    {
      "id": "q1",
      "text": "Что произойдёт при удалении узла с детьми?",
      "multiple": false,
      "options": [
        { "id": "q1o1", "text": "Дети удаляются вместе с узлом", "correct": false },
        { "id": "q1o2", "text": "Дети переходят к родителю удаляемого узла", "correct": true },
        { "id": "q1o3", "text": "Удаление блокируется", "correct": false }
      ]
    },
    {
      "id": "q2",
      "text": "Какие данные сохраняются автоматически?",
      "multiple": true,
      "options": [
        { "id": "q2o1", "text": "Текст и положение узлов", "correct": true },
        { "id": "q2o2", "text": "Заметки", "correct": true },
        { "id": "q2o3", "text": "История прохождения всех попыток теста", "correct": false }
      ]
    }
  ]
}
```

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `title` | string | нет | Заголовок теста в панели. Если не задан — приложение использует `node.text` узла. |
| `description` | string (Markdown) | нет | Описание/инструкция, показывается на стартовом экране теста. |
| `passThreshold` | number (0–100) | **да** | Минимальный процент правильных ответов, при котором тест считается пройденным. |
| `estimatedMinutes` | number | нет | Ориентировочное время прохождения (в минутах), показывается на стартовом экране. Если не задано, приложение вычисляет оценку как `max(1, round(questions.length * 1.5))`. |
| `questions` | array | **да**, минимум 1 элемент | Список вопросов, см. ниже. |

### 4.1 Объект вопроса (`questions[i]`)

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `id` | string | **да** | Уникальный (в пределах теста) идентификатор вопроса. |
| `text` | string (Markdown) | **да** | Текст вопроса. |
| `multiple` | boolean | **да** | `true` — вопрос с несколькими правильными ответами (в UI — чекбоксы, пользователь должен выбрать ВСЕ правильные варианты и ни одного лишнего). `false` — один ответ (в UI — radio-кнопки). |
| `options` | array | **да**, минимум 2 элемента | Варианты ответа, см. ниже. |

### 4.2 Объект варианта ответа (`options[j]`)

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `id` | string | **да** | Уникальный (в пределах вопроса) идентификатор варианта. |
| `text` | string (Markdown) | **да** | Текст варианта ответа. |
| `correct` | boolean | **да** | `true`, если это правильный вариант. |

**Важные правила при генерации вопросов:**
- У каждого вопроса должен быть **минимум один** вариант с `"correct": true`.
- Если `multiple: false` (один ответ) — ровно **один** вариант должен иметь `"correct": true`.
- Если `multiple: true` (несколько ответов) — можно иметь **два и более** правильных вариантов
  (если правильный только один — используйте `multiple: false`, это семантически корректнее и
  отображается как radio, а не чекбокс).
- Правило проверки ответа в приложении: вопрос засчитывается верным, только если пользователь
  выбрал **ровно** множество вариантов с `correct: true` — не больше и не меньше.
- Не оставляйте `questions` пустым — тест без вопросов приложение не распознаёт как «есть тест»
  (см. `Model.hasTest`, которая проверяет `questions.length > 0`).

## 5. `data.testResult` — результат прохождения (только последняя попытка)

**Это поле пишет только сама программа** во время прохождения теста пользователем. Агенту, как
правило, **не следует** генерировать или изменять `testResult` вручную — оно должно либо
отсутствовать (тест ещё не проходили), либо быть оставлено как есть при импорте/модификации
существующего файла (если вы не трогаете структуру этого конкретного теста).

Формат — для справки, чтобы агент понимал семантику при чтении существующих данных:

```jsonc
"testResult": {
  "completedAt": 1730900000000,
  "status": "passed",
  "correctCount": 8,
  "answeredCount": 10,
  "totalCount": 10,
  "scorePercent": 80,
  "passed": true,
  "elapsedMs": 720000,
  "wrong": [
    {
      "num": 4,
      "questionText": "Какова основная функция цикла Кребса?",
      "yourText": "Производство глюкозы",
      "correctText": "Генерация переносчиков электронов (НАДН, ФАДН2)"
    }
  ]
}
```

| Поле | Тип | Описание |
|---|---|---|
| `completedAt` | number | Unix-время (мс) завершения/прерывания попытки. |
| `status` | `"passed" \| "failed" \| "aborted"` | Пройден / не пройден / прерван пользователем до конца. |
| `correctCount` | number | Число верно отвеченных вопросов. |
| `answeredCount` | number | Число вопросов, на которые был выбран хотя бы один вариант. |
| `totalCount` | number | Общее число вопросов в тесте на момент попытки. |
| `scorePercent` | number | `round(correctCount / totalCount * 100)`. |
| `passed` | boolean | `scorePercent >= passThreshold`. |
| `elapsedMs` | number | Затраченное время в миллисекундах. |
| `wrong` | array | Список неверно отвеченных вопросов (пустой массив, если ошибок нет). `num` — 1-based порядковый номер вопроса в тесте на момент попытки; `questionText`/`yourText`/`correctText` — обычный текст (Markdown уже убран), а не разметка. |

**Важно:** история попыток НЕ хранится — `testResult` всегда представляет только самую последнюю
попытку и полностью перезаписывается при следующей.

**Если вы (агент) генерируете новый тест или переписываете вопросы существующего теста** — удалите
поле `testResult` у этого узла (старый результат относится к другому набору вопросов и станет
неактуальным/бессмысленным).

## 6. Поддерживаемый Markdown (для `note`, `test.description`, `questions[].text`, `options[].text`)

Все Markdown-поля рендерятся общим упрощённым конвертером приложения. Поддерживается **ровно**
следующий набор конструкций — не полагайтесь на полный CommonMark:

- Заголовки: строки, начинающиеся с `#` до `######` (`# Заголовок` … `###### Заголовок`).
- Списки:
  - маркированный — строка начинается с `- ` или `* `;
  - нумерованный — строка начинается с `N. ` (например `1. `, `2. `).
- Инлайн-форматирование:
  - полужирный: `**текст**` или `__текст__`;
  - курсив: `*текст*` или `_текст_`;
  - подчёркнутый: `<u>текст</u>` (единственный разрешённый «сырой» HTML-тег);
  - ссылка: `[текст](url)`;
  - изображение: `![alt](url)` (только внешние URL, без вставки файлов).
- Обычные непустые строки вне списков — отдельные абзацы.
- Любой другой HTML в тексте будет экранирован (отображён как текст, а не выполнен) — не
  полагайтесь на произвольную HTML-разметку внутри Markdown-полей.

## 7. Версионирование формата

| Версия | Что добавилось |
|---|---|
| 1 | Базовый формат: `id/type/text/parentId/data` (data почти всегда `{}`), направление ветвей уже было. |
| 2 | `data.offset` — ручное смещение узла. |
| 3 | `data.note` — Markdown-заметка. |
| 4 | `data.test` и `data.testResult` — тестирование. |
| **5 (текущая)** | `data.marked` — визуальная отметка узла (зелёная рамка). |

- Всегда указывайте `"version": 5` при генерации/сохранении файла с нуля.
- При импорте более старого файла (`version` 1–4) — можно смело добавлять новые поля (`test`,
  `note`, `marked` и т.д.) прямо поверх, приложение обратно совместимо. Обновите `version` на `5` в
  результирующем файле.
- Приложение не проверяет строго содержимое `nodes[*].data` по схеме — валидируется только верхний
  уровень (`version` присутствует, `rootId` — строка, `nodes` — объект, `nodes[rootId]` существует).
  Тем не менее агент должен придерживаться описанных выше схем полей `data.*`, иначе соответствующий
  UI (панель заметок/тестов) будет вести себя непредсказуемо или проигнорирует данные.

## 8. Пример минимального валидного файла

```json
{
  "version": 4,
  "rootId": "n1",
  "nodes": {
    "n1": {
      "id": "n1",
      "type": "main",
      "text": "Корневая тема",
      "parentId": null,
      "data": {}
    },
    "n2": {
      "id": "n2",
      "type": "main",
      "text": "Подтема",
      "parentId": "n1",
      "data": { "direction": "right", "note": "Заметка о подтеме" }
    },
    "n3": {
      "id": "n3",
      "type": "test",
      "text": "Проверь себя",
      "parentId": "n1",
      "data": {
        "direction": "left",
```

## 9. Чек-лист для агента перед выдачей результата

1. `version` = 5.
2. Ровно один узел с `parentId: null`, и он совпадает с `rootId`.
3. У всех остальных узлов `parentId` ссылается на существующий id.
4. Нет циклов в цепочках `parentId`.
5. У каждого прямого ребёнка корня задан `data.direction` (`up`/`down`/`left`/`right`).
6. У узлов, не являющихся прямыми детьми корня, `data.direction` отсутствует.
7. `type` — один из `"main" | "test" | "link"`.
8. Если задан `data.test`: есть `passThreshold` (0–100) и непустой `questions[]`; у каждого вопроса
   — корректное количество правильных вариантов согласно `multiple`.
9. Не сгенерирован `data.testResult` для нового/изменённого теста (или он корректно удалён при
   изменении структуры существующего теста).
10. Пустые/неактуальные атрибуты (`comment`, `note`, `offset`) не выставлены пустыми строками —
    просто отсутствуют как ключи.
11. `data.marked` установлен только там, где узел действительно должен быть отмечен (`true`);
    не отмеченным узлам это поле не добавлено, и оно не установлено у корня.
