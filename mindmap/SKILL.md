# Работа с данными Mind Map (агент-наполнитель без доступа к файловой системе приложения)

Создаёт, читает и модифицирует диаграмму jLearn Mind Map исключительно как JSON-текст: на входе —
экспортированный файл диаграммы (или его отсутствие), на выходе — полный обновлённый JSON того же
формата, готовый к импорту в приложение. У тебя НЕТ доступа к коду или файловой системе приложения —
всё, что нужно знать о формате, описано ниже.

## Критические ограничения

- Работай ТОЛЬКО с данными, явно переданными в диалоге (вставленный JSON, прикреплённый файл). Не
  предполагай доступ к другим файлам приложения, не читай и не пиши ничего, кроме итогового JSON,
  который ты возвращаешь пользователю.
- Никогда не меняй структуру полей, не изобретай новые поля `data.*` и не вводи новые значения
  `type`, кроме описанных в разделе «Типы узлов» — реестр типов зашит в коде приложения, ты не можешь
  его расширить через данные.
- Не генерируй и не изменяй `data.testResult` вручную (раздел «Результат теста») — это поле пишет
  только само приложение во время прохождения теста пользователем. Исключение: если ты меняешь
  структуру/вопросы существующего теста узла — удали устаревший `testResult` этого узла.
- Всегда возвращай ПОЛНЫЙ валидный JSON целиком (весь объект `{version, rootId, nodes}`), а не diff
  и не фрагмент — приложение читает файл целиком при импорте.
- Перед выдачей результата пройди чек-лист валидации (раздел «Чек-лист перед выдачей»); если что-то
  не проходит — исправь, не выдавай частично невалидный результат.

## Входные данные

- **Запрос пользователя** на естественном языке: создать новую схему, добавить/изменить/удалить
  узел, добавить или отредактировать заметку, создать/изменить тест, отметить узел, и т.п.
- **Текущий файл диаграммы** (необязательно): JSON в формате ниже, вставленный в диалог или
  прикреплённый файл. Если пользователь не предоставил файл и просит что-то создать — начинай с
  нуля по шаблону из раздела «Создание диаграммы с нуля».

## Формат данных (version 5)

```jsonc
{
  "version": 5,
  "rootId": "n1",
  "nodes": {
    "n1": { "id": "n1", "type": "main", "text": "Заголовок", "parentId": null, "data": {} },
    "n2": { "id": "n2", "type": "main", "text": "Подтема", "parentId": "n1",
      "data": { "direction": "right" } }
  }
}
```

- `version` — всегда пиши `5`.
- `rootId` — id корневого узла (единственный узел с `parentId: null`).
- `nodes` — плоский словарь `{id: node}`. Дерево строится через `parentId`, НЕ через вложенность.

### Правила дерева

- Ровно один узел с `parentId: null`, и это `rootId`.
- У всех остальных узлов `parentId` ссылается на существующий id в `nodes`.
- Циклы через цепочку `parentId` запрещены.
- Корень нельзя удалить и нельзя дать ему `data.direction`/`data.offset`/`data.marked`.
- `id` — любая уникальная непустая строка в пределах файла (например `"n1"`, `"n2"`, ... или UUID).

### Объект узла

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `id` | string | да | Совпадает с ключом в `nodes`. |
| `type` | string | да | `"main"` \| `"test"` \| `"link"` (см. «Типы узлов»). |
| `text` | string | да | Заголовок узла на диаграмме. Обычный текст, НЕ Markdown. |
| `parentId` | string\|null | да | `null` только у корня. |
| `data` | object | да (может быть `{}`) | Необязательные атрибуты ниже — отсутствие ключа = «не задано». |

### Атрибуты `data.*`

- **`direction`** (`"up"\|"down"\|"left"\|"right"`): диаграмма радиальная, корень в центре. Обязательно
  задавай у ПРЯМЫХ детей корня (`parentId === rootId`); если направление не важно — используй
  `"right"`. НЕ добавляй это поле более глубоким узлам (они наследуют направление ветви автоматически).
- **`comment`** (string): короткая (можно многострочная) подпись под узлом мелким шрифтом. НЕ Markdown.
  Не добавляй ключ, если комментария нет (не пиши пустую строку).
- **`note`** (string, Markdown): полноценная заметка узла — см. «Поддерживаемый Markdown». Не
  добавляй ключ, если заметки нет.
- **`offset`** (`{dx:number, dy:number}`): ручное пиксельное смещение узла на холсте. Обычно НЕ
  устанавливай это поле сам — оставляй узел на автоматической позиции. Если меняешь `parentId`
  существующего узла — удали его `offset` (смещение теряет смысл при смене родителя).
- **`test`** (object): определение теста — см. «Тест: определение».
- **`testResult`** (object): результат последней попытки — см. «Тест: результат» (не создавай/не
  меняй вручную, кроме удаления при смене вопросов).
- **`marked`** (boolean): чисто визуальная зелёная рамка («выполнено»). Пиши `true` только когда
  нужно отметить узел; не пиши `false` — используй отсутствие поля. Не ставь у корня.

### Типы узлов (`type`) — фиксированный список, расширять нельзя

| `type` | Название в UI | Когда использовать |
|---|---|---|
| `"main"` | Узел | По умолчанию для любого смыслового узла. |
| `"test"` | Тест | Узел, к которому привязан `data.test` — приложение показывает кнопку прохождения теста при клике на узел этого типа. |
| `"link"` | Ссылка | Смысловая пометка «это ссылка на внешний ресурс»; URL принято класть в `data.comment`. |

Если пользователь просит новый тип узла — сообщи, что это невозможно через данные (типы зашиты в
коде приложения); предложи ближайший существующий тип + `comment`/`note` для уточнения.

### Тест: определение (`data.test`)

```jsonc
"test": {
  "title": "Заголовок теста",
  "description": "Инструкция, Markdown",
  "passThreshold": 70,
  "estimatedMinutes": 10,
  "questions": [
    {
      "id": "q1",
      "text": "Текст вопроса, Markdown",
      "multiple": false,
      "options": [
        { "id": "q1o1", "text": "Вариант A", "correct": false },
        { "id": "q1o2", "text": "Вариант B", "correct": true }
      ]
    }
  ]
}
```

- `title` (опц.) — если не задан, приложение берёт `node.text` узла.
- `description` (опц., Markdown) — показывается на стартовом экране.
- `passThreshold` (обяз., 0–100) — % правильных ответов для «пройдено».
- `estimatedMinutes` (опц.) — иначе оценивается как `max(1, round(N_вопросов * 1.5))`.
- `questions` (обяз., минимум 1): каждый вопрос — `id`, `text` (Markdown), `multiple` (bool),
  `options` (минимум 2, каждый — `id`, `text` (Markdown), `correct` (bool)).
- Правила подсчёта: вопрос засчитан верным, только если пользователь выбрал РОВНО множество
  вариантов с `correct: true` (не больше, не меньше).
  - `multiple: false` (один ответ, radio) → ровно один вариант с `correct: true`.
  - `multiple: true` (чекбоксы) → два и более вариантов с `correct: true` (если правильный только
    один — используй `multiple: false`).
- У каждого вопроса минимум один правильный вариант. Пустой `questions` недопустим.

### Тест: результат (`data.testResult`) — только для чтения

Пишется приложением при завершении/прерывании попытки: `completedAt`, `status`
(`"passed"|"failed"|"aborted"`), `correctCount`, `answeredCount`, `totalCount`, `scorePercent`,
`passed`, `elapsedMs`, `wrong[]` (`{num, questionText, yourText, correctText}`). Хранится только
последняя попытка. Ты можешь ПРОЧИТАТЬ это поле, чтобы понять статус прохождения, но не создавай и
не редактируй его — только удаляй целиком, если меняешь вопросы этого теста.

### Поддерживаемый Markdown (для `note`, `test.description`, `questions[].text`, `options[].text`)

Ограниченное подмножество — НЕ полагайся на полный CommonMark:
- Заголовки `#` … `######`.
- Списки: `- `/`* ` (маркированный), `N. ` (нумерованный).
- Инлайн: `**bold**`/`__bold__`, `*italic*`/`_italic_`, `<u>underline</u>` (единственный разрешённый
  сырой HTML-тег), `[текст](url)`, `![alt](url)`.
- Прочие непустые строки вне списков — отдельные абзацы.
- Любой другой HTML экранируется (отображается как текст).

## Алгоритм

1. **Разбери входные данные.** Если пользователь дал файл/JSON — распарси его, проверь, что это
   валидная структура (`version`, `rootId`, `nodes`, `nodes[rootId]` существует). Если файла нет —
   переходи к «Созданию диаграммы с нуля».
2. **Определи тип операции** из запроса пользователя: создание новой диаграммы, добавление узла,
   редактирование текста/атрибутов, удаление узла, перемещение узла, создание/правка теста,
   добавление/правка заметки, отметка узла. Смешанные запросы — выполняй последовательно.
3. **Примени операцию**, используя правила из раздела «Типовые операции» ниже.
4. **Обнови `version` до 5**, если исходный файл был более старой версии — просто добавляй новые
   поля поверх существующих данных, ничего не удаляя из старых (обратная совместимость).
5. **Пройди «Чек-лист перед выдачей»** — если что-то не проходит, исправь и проверь снова.
6. **Верни результат** по правилам раздела «Формат вывода».

## Типовые операции

- **Создание диаграммы с нуля**: один корневой узел `type: "main"`, `parentId: null`, `data: {}`,
  `text` — тема, заданная пользователем. Остальные узлы — его потомки (прямые дети получают
  `direction`, распредели по 4 направлениям для баланса, если пользователь не указал иное).
- **Добавление узла**: новый `id`, `type` по смыслу запроса (по умолчанию `"main"`), `text`,
  `parentId` — id существующего узла. Если `parentId === rootId` — обязательно задай `direction`.
- **Редактирование текста/атрибутов**: меняй только запрошенные поля, не трогай остальные (включая
  чужой `offset`/`testResult`, если явно не просили).
- **Удаление узла**: удали узел из `nodes`; ЕГО ДЕТЕЙ (если есть) перепривяжи к его бывшему
  `parentId` (переприсвой их `parentId` на родителя удаляемого узла) — это НЕ каскадное удаление,
  так себя ведёт и само приложение. Нельзя удалять корень.
- **Перемещение узла** (смена родителя): обнови `parentId`; удали `offset` этого узла; если новый
  родитель — корень, задай/сохрани `direction`, иначе убери `direction`, если он был (наследуется).
- **Создание/правка теста**: заполни `data.test` по схеме выше у узла (обычно `type: "test"`); при
  изменении вопросов существующего теста — удали устаревший `data.testResult`.
- **Добавление/правка заметки**: запиши Markdown-текст в `data.note`; убери поле целиком, если
  пользователь просит удалить заметку (не оставляй пустую строку).
- **Отметка узла**: `data.marked: true` (или убери поле для снятия отметки); не для корня.

## Формат вывода

Верни ОДИН блок кода с полным обновлённым JSON (весь файл `{version, rootId, nodes}`), без
сокращений и без пояснений внутри блока. После блока кратко (2–5 пунктов) опиши на естественном
языке, что именно изменено.

## Чек-лист перед выдачей

1. `"version": 5`.
2. Ровно один узел с `parentId: null`; он совпадает с `rootId`.
3. У всех остальных узлов `parentId` указывает на существующий id.
4. Нет циклов в цепочках `parentId`.
5. Каждый прямой ребёнок корня имеет `data.direction`; более глубокие узлы — не имеют.
6. `type` каждого узла — один из `"main"|"test"|"link"`.
7. Если есть `data.test`: `passThreshold` задан (0–100), `questions` непустой, у каждого вопроса
   верное число правильных вариантов согласно `multiple`.
8. `data.testResult` не создан/не изменён вручную для нового или структурно изменённого теста.
9. `comment`/`note`/`offset` не выставлены как пустые строки — при отсутствии значения ключ просто
   не добавлен.
10. `data.marked` установлен только там, где нужно, и никогда — у корня.
